# 알림 시스템 아키텍처 기록

> 과거 설계/리팩토링 설명을 보존한 문서이며 예약 기능의 구현 API 명세가 아닙니다. 아래 내용은 게시 코드 `3865b451663788792d7e78c736282f8b9ff105f1`과 대조해 보정했습니다. 운영 배포·실제 수신 또는 테스트 통과를 확인한 기록은 아닙니다. 현재 API 계약은 [SSE 가이드](../notification/SSE_NOTIFICATION_GUIDE.md)를 우선합니다.

## 1. 핵심 설계 원칙 (Synchronous Save + Asynchronous Delivery)
본 프로젝트의 알림 시스템은 **데이터 정합성(Consistency)**과 **응답 속도(Performance)**를 모두 만족시키기 위해 **"동기 저장 후 비동기 전송"** 방식을 채택했습니다.

### 1.1 저장 (Persistence): 동기 처리 (Synchronous)
- **방식**: `ProjectApplicationServiceImpl` 등 메인 비즈니스 트랜잭션에서 `NotificationSaveService`를 호출하여 저장합니다.
- **이유**: 알림은 사용자에게 중요한 히스토리 데이터입니다. 메인 로직(지원, 승인 등)이 성공했다면, 알림 내역 또한 **반드시 DB에 저장됨을 보장(Atomicity)**해야 합니다.

### 1.2 전송 (Delivery): 비동기 처리 (Asynchronous)
- **방식**: 비즈니스 트랜잭션 안에서 이벤트를 발행하고, 커밋된 후(`AFTER_COMMIT`) 리스너가 비동기로 처리하여 `SSENotificationService`에서 별도의 스레드로 SSE(Server-Sent Events)를 전송합니다.
- **이유**: 외부 네트워크 통신(SSE 연결)이나 전송 지연이 사용자 경험(API 응답 속도)에 영향을 주지 않도록 하기 위함입니다. 전송이 실패하더라도 이미 저장된 DB 데이터는 안전합니다.

## 2. 상세 프로세스

### 2.1 일반 알림 (지원, 승인, 거절 등)
대부분의 1:1 알림(`PROJECT_APPLY`, `PROJECT_MY_APPLY`, `PROJECT_APPROVE`, `PROJECT_REJECT`)은 아래 흐름을 따릅니다.

1.  **Service (Main Transaction)**
    *   비즈니스 로직 수행 (예: 지원서 저장)
    *   **`Notification` 엔티티 생성 및 저장 (INSERT)**
    *   `NotificationEvent` 발행
2.  **NotificationListener**
    *   트랜잭션 커밋 후 이벤트 수신
    *   `SSENotificationService.notify()` 호출 (비동기)
3.  **SSENotificationService**
    *   전달받은 정보로 `Payload` 생성
    *   **Redis 시퀀스 발급 → 캐시 저장 → Pub/Sub 발행** (수신 인스턴스가 로컬 SSE로 전송, 전달 ACK 없음)
    *   *저장 로직 없음 (이미 1단계에서 저장됨)*

### 2.2 배치성 알림 (프로젝트 종료)
현재 게시 코드에서는 프로젝트 삭제 시에도 **동기 알림 저장 후 커밋 이후 비동기 전파**를 사용합니다. 과거의 전체 비동기 저장 설명은 더 이상 현재 구현이 아닙니다.
- `ProjectCommandServiceImpl.delete()`에서 멤버를 조회하고 `saveForProjectEnd(project, members)`를 호출한 다음 ID 목록·프로젝트 이름을 담은 `ProjectEndEvent`를 발행합니다.
- `NotificationListener`는 커밋 이후 비동기로 처리하며 `SSENotificationService.notify(ProjectEndEvent)`는 전달된 멤버 ID별 payload를 만들어 전파합니다. 여기서 알림을 DB에 다시 저장하거나 삭제된 프로젝트에서 멤버를 다시 조회하지 않습니다.
- 근거(위 커밋, `src/main/java/com/wardk/meeteam_backend/` 기준): `domain/project/service/ProjectCommandServiceImpl.java:98-115`, `domain/notification/NotificationListener.java:28-40`, `domain/notification/service/SSENotificationService.java:77-103`.

## 3. 리팩토링 히스토리 & 변경 사항

### 3.1 주요 변경 사항
- **구조 변경**: `SSENotificationService`에서 수행하던 알림 저장을 `ProjectApplicationService` 등 호출부로 이동하여 데이터 유실 가능성을 차단했습니다.
- **NotificationType 이름 변경**: API 명세 일치 (`PROJECT_SELF_APPLY` -> `PROJECT_MY_APPLY` 등).
- **이중 저장 방지**: 서비스 계층에서 저장하고, SSE 서비스에서는 전송만 담당하도록 역할을 엄격히 분리했습니다.

## 검증 경계

DB 원자성은 해당 비즈니스 트랜잭션의 저장 경로에 대한 설명이지 실시간 전달 성공 보장이 아닙니다. 커밋 후 프로세스 종료/비동기 실패를 위한 durable outbox, SSE ACK·재시도는 이 흐름에 없습니다. Redis 장애·캐시 만료 후 replay 성공을 보장하지 않습니다. 근거: `domain/application/service/ProjectApplicationServiceImpl.java:126-145,237-251,264-278`, `domain/notification/service/SSENotificationService.java:137-164`.
