# 인증 테스트 시나리오

테스트 계정 생성·로그인과 일반 회원의 인증 분기를 확인합니다. 대상은 `TestAccountServiceTest` 14개와 `TestAccountSejongLoginTest` 4개, 총 **단위 테스트 18개**입니다.

기준 코드는 `b57d461`이며 로컬 미완료 수정은 제외했습니다. 기존 코드를 읽고 정리한 문서로, 테스트는 아직 실행하지 않았습니다.

[실행 방법](../README.md) · [결과 양식](../results/TEMPLATE.md)

## 1. 용어

| 용어 | 설명 |
| --- | --- |
| 단위 테스트 | 작은 기능을 따로 확인하는 자동 검사 |
| 대역(mock) | DB·포털 대신 정해진 응답을 주는 가짜 기능 |
| 토큰 | 로그인 증표. 여기서는 더미 값 사용 |
| 쿠키 | 브라우저가 보관해 요청에 보내는 정보 |
| 해시 | 비밀번호 원문 대신 저장하는 비교용 값 |
| 프로파일 | 운영·테스트 등 실행 환경 설정 |
| 설정 확인 공간 | 전체 서버 대신 필요한 구성만 띄워 등록 조건을 확인하는 공간 |

아래 절차는 사이트에서 버튼을 누르는 순서가 아니라 자동 테스트가 수행하는 행동입니다. 개발자가 실행하고 검토자는 기대 결과와 보고서를 대조합니다.

## 2. 준비와 실행

- 공통 환경·명령은 [실행 안내](../README.md)의 3~6절을 따릅니다.
- 실제 계정 대신 더미 회원·비밀번호를 사용합니다. 회원 저장소·토큰 발급기·포털은 대역으로 준비합니다.
- 각 테스트를 새 조건에서 시작합니다. 실제 DB를 비우거나 포털에 접속하지 않습니다.
- 외부 환경변수가 활성화·비밀번호 설정을 주입하지 않는지 확인합니다. 특히 설정 누락을 검사하는 UT-11·UT-14에 영향을 줄 수 있습니다.

## 3. 시나리오

### UT-01. 예약된 테스트 계정을 안전하게 만든다

- **준비:** 테스트 계정이 저장돼 있지 않다고 가정합니다. 테스트 전용 더미 비밀번호를 사용합니다.
- **절차:**
  1. 계정 준비 기능을 한 번 실행합니다.
  2. 저장하도록 요청한 회원 정보를 확인합니다.
- **기대 결과:** 예약된 내부 이메일, 일반 회원 권한, 비밀번호 해시가 일치합니다. 비밀번호 원문과 저장값이 다르며 학번 필드는 비어 있습니다.
- **참고:** 실제 DB 저장이나 웹 로그인을 실행하지 않습니다.
- **코드:** `TestAccountServiceTest.createsOnlyReservedUserWithHashedPassword()`

### UT-02. 이미 있는 테스트 계정을 덮어쓰지 않는다

- **준비:** 예약된 계정이 있고 저장된 비밀번호 해시가 설정과 일치한다고 가정합니다.
- **절차:**
  1. 계정 준비 기능을 실행합니다.
  2. 새 회원을 저장하라는 요청이 발생했는지 확인합니다.
- **기대 결과:** 회원 저장 기능을 호출하지 않습니다.
- **참고:** 모든 회원 필드의 변경 전후를 비교하는 테스트는 아닙니다.
- **코드:** `TestAccountServiceTest.preservesExistingTestAccount()`

### UT-03. 비밀번호가 다른 기존 계정을 임의로 바꾸지 않는다

- **준비:** 예약된 내부 이메일의 계정이 있지만 저장된 비밀번호가 설정과 다르다고 가정합니다.
- **절차:**
  1. 계정 준비 기능을 실행합니다.
  2. 중단 오류와 저장 요청 여부를 확인합니다.
- **기대 결과:** 안전하게 중단하는 오류가 발생하고 회원 저장 기능은 호출하지 않습니다.
- **참고:** 실제 서버 재시작이나 DB 복구까지 확인하는 테스트는 아닙니다.
- **코드:** `TestAccountServiceTest.refusesToOverwriteAccountWithDifferentPassword()`

### UT-04. 올바른 테스트 계정으로 로그인 처리를 한다

- **준비:** 예약 계정과 올바른 더미 비밀번호를 준비합니다. 로그인 증표 발급기는 더미 값을 반환하도록 둡니다.
- **절차:**
  1. 예약된 로그인 ID와 올바른 비밀번호로 로그인 처리를 요청합니다.
  2. 반환 결과와 증표 발급 요청을 확인합니다.
- **기대 결과:** 결과가 비어 있지 않고 접근용·갱신용 증표 발급 기능이 각각 호출됩니다.
- **참고:** 실제 JWT의 서명·유효기간·브라우저 사용 가능 여부는 확인하지 않습니다.
- **코드:** `TestAccountServiceTest.acceptsReservedAccountAndIssuesTokens()`

### UT-05. 잘못된 비밀번호를 거부한다

- **준비:** 예약 계정은 존재하지만 입력 비밀번호를 저장된 값과 다르게 준비합니다.
- **절차:**
  1. 잘못된 비밀번호로 로그인 처리를 요청합니다.
  2. 거부 오류가 발생하는지 확인합니다.
  3. 증표 발급기를 호출했는지 확인합니다.
- **기대 결과:** 거부 오류가 발생하고 증표 발급기는 호출하지 않습니다.
- **참고:** 오류 종류를 확인하지만 정확한 오류 코드·메시지·HTTP 상태는 검사하지 않습니다.
- **코드:** `TestAccountServiceTest.wrongPasswordCannotIssueTokens()`

### UT-06. 예약되지 않은 ID로 테스트 로그인을 할 수 없다

- **준비:** 예약된 숫자 ID가 아닌 다른 ID를 입력합니다.
- **절차:**
  1. 다른 ID로 테스트 로그인을 요청합니다.
  2. 회원 조회와 증표 발급 요청 여부를 확인합니다.
- **기대 결과:** 거부 오류가 발생하고 회원 저장소와 증표 발급기를 호출하지 않습니다.
- **참고:** 일반 회원의 세종대 로그인이 금지된다는 뜻이 아닙니다. 테스트 전용 로그인 기능의 제한입니다.
- **코드:** `TestAccountServiceTest.cannotLoginAsOtherMember()`

### UT-07. 내부 이메일을 로그인 ID로 사용하지 못하게 한다

- **준비:** 계정을 저장할 때 사용하는 내부 이메일을 로그인 ID로 입력합니다.
- **절차:**
  1. 내부 이메일로 테스트 로그인을 요청합니다.
  2. 오류와 의존 기능 호출 여부를 확인합니다.
- **기대 결과:** 거부 오류가 발생하고 회원 저장소와 증표 발급기를 호출하지 않습니다.
- **참고:** 공개 로그인 ID인 99990001과 내부 저장용 이메일을 구분하는 검사입니다.
- **코드:** `TestAccountServiceTest.internalEmailIsNotAcceptedAsTheLoginId()`

### UT-08. 잘못된 로그인을 반복해도 증표를 발급하지 않는다

- **준비:** 잘못된 ID와 비밀번호로 11번 요청할 준비를 합니다.
- **절차:**
  1. 잘못된 로그인 요청을 11번 반복합니다.
  2. 각 요청에서 거부 오류가 발생하는지 확인합니다.
  3. 증표 발급 요청이 없었는지 확인합니다.
- **기대 결과:** 11번 모두 거부 오류가 발생하고 증표 발급기를 호출하지 않습니다.
- **참고:** 메서드 이름은 시도 제한을 뜻하지만, 이 검증만으로 10회까지 허용·11회부터 제한 또는 1분 뒤 해제를 입증할 수 없습니다. 입력 자체가 처음부터 잘못됐기 때문입니다.
- **코드:** `TestAccountServiceTest.rateLimitsAttempts()`

### UT-09. 너무 짧거나 바이트 제한을 넘는 설정을 거부한다

- **준비:** 짧은 문자열과, 한글 25자처럼 UTF-8 기준 72바이트를 초과하는 더미 값을 각각 준비합니다.
- **절차:**
  1. 짧은 비밀번호로 테스트 계정 기능을 구성합니다.
  2. 너무 긴 비밀번호로 같은 구성을 시도합니다.
- **기대 결과:** 두 경우 모두 잘못된 설정이라는 오류가 발생합니다.
- **참고:** 최소 16자·최대 72바이트의 정확한 경계값 전체를 검사하는 테스트는 아닙니다. 실제 비밀번호를 문서에 적지 않습니다.
- **코드:** `TestAccountServiceTest.rejectsWeakOrOverlongPassword()`

### UT-10. 컨트롤러가 쿠키 설정을 요청하고 증표를 본문에 넣지 않는다

- **준비:** 로그인 기능과 쿠키 설정 기능을 대역으로 준비합니다. 실제 브라우저가 아닌 가상 응답을 사용합니다.
- **절차:**
  1. 테스트 로그인 컨트롤러를 직접 호출합니다.
  2. 접근용·갱신용 쿠키 설정 기능의 호출을 확인합니다.
  3. 응답의 결과 본문과 로그인 요청의 문자열 표현을 확인합니다.
- **기대 결과:** 쿠키 설정 기능 2개를 올바른 더미 값으로 호출합니다. 결과 본문은 비어 있고 요청 문자열 표현에 비밀번호 원문이 포함되지 않습니다.
- **참고:** 쿠키 설정기를 대역으로 사용하므로 실제 Set-Cookie·HttpOnly·Secure·SameSite나 모든 로그의 비밀번호 마스킹을 검증하지 않습니다.
- **코드:** `TestAccountServiceTest.controllerSetsBothStandardCookiesWithoutReturningTokens()`

### UT-11. 테스트 환경이어도 기본값으로는 전용 로그인을 켜지 않는다

- **준비:** test 환경만 지정하고 활성화 설정은 주지 않습니다.
- **절차:**
  1. 작은 설정 확인용 실행 공간을 만듭니다.
  2. 시작 오류와 테스트 계정 서비스·컨트롤러 등록 수를 확인합니다.
- **기대 결과:** 설정 확인 공간은 정상 시작하지만 서비스와 컨트롤러는 각각 0개입니다.
- **참고:** 전체 애플리케이션이나 HTTP 주소를 실제로 기동하는 테스트가 아닙니다.
- **코드:** `TestAccountServiceTest.disabledByDefaultEvenInTestProfile()`

### UT-12. 운영 환경에서는 활성화 설정을 줘도 전용 로그인을 만들지 않는다

- **준비:** prod, production, test+prod, test+production, dev 환경에 각각 활성화 설정을 줍니다.
- **절차:**
  1. 환경 조합을 하나씩 적용합니다.
  2. 시작 오류와 서비스·컨트롤러 등록 수를 확인합니다.
- **기대 결과:** 각 설정 확인 공간은 정상 시작하고 전용 서비스·컨트롤러는 각각 0개입니다.
- **참고:** 임의의 모든 환경 이름이나 실제 운영 배포를 검사한 결과는 아닙니다.
- **코드:** `TestAccountServiceTest.unavailableOutsideTestAndInProductionEvenWhenEnabled()`

### UT-13. 필요한 조건을 갖췄을 때만 전용 로그인을 준비한다

- **준비:** test 환경, 명시적인 활성화 설정, 유효한 더미 비밀번호를 함께 지정합니다.
- **절차:**
  1. 세 가지 조건으로 설정 확인 공간을 시작합니다.
  2. 서비스·컨트롤러 등록 수를 확인합니다.
- **기대 결과:** 시작 오류가 없고 전용 서비스·컨트롤러가 각각 1개입니다.
- **참고:** 계정이 실제 DB에 생성되거나 웹 로그인이 성공했음을 뜻하지 않습니다.
- **코드:** `TestAccountServiceTest.enabledOnlyWithTestProfileAndExplicitSwitchAndPassword()`

### UT-14. 비밀번호 설정이 없으면 안전하게 시작을 중단한다

- **준비:** test 환경과 활성화 설정만 주고 비밀번호는 지정하지 않습니다. 외부 환경변수에서도 값이 들어오지 않게 해야 합니다.
- **절차:**
  1. 해당 설정으로 작은 실행 공간을 시작합니다.
  2. 시작 실패 여부를 확인합니다.
- **기대 결과:** 시작 실패가 기록됩니다.
- **참고:** 정확한 실패 메시지나 전체 서버 기동 경로는 검사하지 않습니다.
- **코드:** `TestAccountServiceTest.missingPasswordFailsClosed()`

### UT-15. 전용 테스트 계정은 세종대 포털에 접속하지 않는다

- **준비:** 전용 테스트 로그인 기능을 사용할 수 있고 예약 ID 인증이 성공하도록 대역을 준비합니다.
- **절차:**
  1. 예약 ID 99990001로 세종대 로그인 업무를 요청합니다.
  2. 반환 결과와 호출된 기능을 확인합니다.
- **기대 결과:** 기존 회원으로 처리되고 신규 가입 코드는 없습니다. 접근용·갱신용 더미 증표가 있으며 테스트 로그인 기능만 호출합니다. 포털과 회원 저장소는 호출하지 않습니다.
- **참고:** 대역이 성공하도록 설정한 검사입니다. 실제 테스트 계정 비밀번호의 유효성은 확인하지 않습니다.
- **코드:** `TestAccountSejongLoginTest.numericTestAccountUsesVerifiedPasswordWithoutContactingPortal()`

### UT-16. 테스트 계정 인증 실패를 일반 포털 로그인으로 우회하지 않는다

- **준비:** 전용 기능은 켜져 있지만 테스트 계정 인증이 거부되도록 준비합니다.
- **절차:**
  1. 예약 ID로 로그인을 요청합니다.
  2. 오류 이후 포털·회원 저장소·증표 발급기 호출 여부를 확인합니다.
- **기대 결과:** 거부 오류가 발생하고 포털·회원 저장소·증표 발급기를 호출하지 않습니다.
- **참고:** 실제 네트워크 장애나 포털 실패 응답을 확인하는 테스트는 아닙니다.
- **코드:** `TestAccountSejongLoginTest.wrongTestPasswordIsRejectedAndDoesNotFallBackToPortal()`

### UT-17. 일반 회원은 테스트 기능이 켜져 있어도 포털 인증을 거친다

- **준비:** 일반 학번과 기존 회원을 준비하고 포털 대역이 인증 성공을 반환하도록 설정합니다.
- **절차:**
  1. 일반 학번으로 세종대 로그인 업무를 요청합니다.
  2. 포털 인증 호출과 테스트 전용 기능 호출 여부를 확인합니다.
- **기대 결과:** 포털 인증 기능을 호출하고 테스트 전용 로그인 기능은 호출하지 않습니다.

## 4. 공통 함수

- `setup()`: 매 테스트의 대역과 검사 대상을 준비합니다.
- `context()`: 환경별 서비스·컨트롤러 등록 조건을 확인합니다.
- `Member.createForTest(...)`: 저장 없이 테스트용 회원 객체를 만듭니다.
- `when(...).thenReturn(...)`: 대역의 응답을 정합니다.
- `verify(...)`·`verifyNoInteractions(...)`: 필요한 호출과 금지된 호출을 확인합니다.

## 5. 추가 확인할 항목
