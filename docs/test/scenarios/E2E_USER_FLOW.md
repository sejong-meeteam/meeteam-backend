# 사용자 흐름 E2E 테스트 시나리오

로그인부터 프로젝트 생성, 지원, 승인·거절, 결과 확인까지 화면에서 이어지는 흐름을 점검하는 문서이다. **사람이 직접 진행할 수동 시나리오이며, 자동화 코드는 작성하지 않았다. 실제 테스트도 아직 진행하지 않았다.**

게시된 백엔드 코드 `017cbc4`의 기능을 바탕으로 작성한 계획이다. 프론트 화면의 구현 여부와 버튼명은 실행 전에 확인해야 한다. 화면이나 기능을 찾을 수 없으면 추측해서 통과 처리하지 않고 ‘진행 불가’로 기록한다.

준비 조건과 진행 방법은 이 문서 안에서 확인한다. 결과는 마지막 절의 항목에 맞춰 별도 기록한다.

## 1. 준비

- 담당자가 안내한 **테스트 웹사이트 주소**를 사용한다. 백엔드 API 주소와 구분하고 운영 데이터가 있는 환경에서 임의로 진행하지 않는다.
- 사용 승인을 받은 서로 다른 회원 계정 3개를 준비한다. A는 리더, B는 승인받을 지원자, C는 거절될 지원자이다. 하나의 테스트 계정으로 세 역할을 대신하지 않는다.
- 브라우저 프로필을 분리해 A·B·C가 각각 로그인할 수 있게 한다. 시크릿 창 여러 개는 로그인 정보를 공유할 수 있으므로 사용자 프로필을 먼저 확인한다.
- 세 계정은 가입된 상태를 기준으로 한다. 신규 회원가입은 이번 흐름의 범위가 아니다.
- 이름에 실행 시각을 넣은 새 프로젝트를 사용한다. 재실행할 때도 새 프로젝트를 만들어 이전 지원·승인 기록과 섞이지 않게 한다.
- 화면명·버튼명은 설명용이다. 같은 역할의 기능을 사용하고 실제 명칭이 다르면 기록한다.
- 알림 도착을 관찰할 시간은 시작 전에 정해 결과에 적는다. 아래 절차는 사이트에서 직접 진행하므로 Gradle 명령이나 SQL 실행은 필요하지 않다.

### 프로젝트 입력값

| 항목 | 입력값 |
| --- | --- |
| 이름 | `E2E_팀원모집_실행일시` |
| 설명 | `사용자 흐름 확인용 프로젝트이다.` |
| 카테고리 / 플랫폼 | 동아리 / 웹 |
| 리더 역할 | 서비스 기획 |
| 모집 역할 / 인원 | 백엔드 Java/Spring / 2명 |
| 필요 기술 | 화면의 선택지에 있는 Java, Spring Boot |
| 마감 방식 | 모집 완료 시 |

리더 역할을 모집 역할과 다르게 두어 인원 계산을 구분한다. 다른 필수 입력이 있으면 테스트용 값으로 채우고 결과에 기록한다. 계정 비밀번호는 문서나 캡처에 남기지 않는다.

## 2. E2E-01: 지원자가 승인받아 팀원이 된다

**시작 조건:** A·B가 로그인할 수 있고 B는 새 프로젝트에 지원하거나 참여한 이력이 없는 상태이다.

| 순서 | 진행할 행동 | 기대 결과 |
| --- | --- | --- |
| 1 | A로 로그인하고 내 프로필을 확인한다. | A의 정보가 표시된다. |
| 2 | 프로젝트 등록 화면에서 준비한 값을 입력하고 등록한다. | 프로젝트가 생성되고 상세 화면에서 입력한 내용을 확인할 수 있다. |
| 3 | 리더와 모집 정보를 확인하고 프로젝트 주소를 기록한다. | A가 리더이며 Java/Spring 2명을 모집하는 상태이다. |
| 4 | A의 화면을 열어 둔 채 B의 브라우저에서 로그인한다. | B의 프로필이 표시되고 A의 로그인과 섞이지 않는다. |
| 5 | B가 기록한 주소로 프로젝트를 열고 Java/Spring을 선택한다. | A가 만든 프로젝트와 모집 역할이 맞게 표시된다. |
| 6 | B가 지원 동기를 적고 지원한다. | 지원이 접수되고 대기 상태가 된다. |
| 7 | A가 지원자 목록과 B의 지원 내용을 확인한다. | B의 이름·지원 역할·지원 동기가 일치한다. |
| 8 | A가 B의 지원을 승인한다. | B의 지원 상태가 승인으로 바뀐다. |
| 9 | 팀원 목록과 모집 역할의 참여 인원을 확인한다. | B가 팀원으로 추가되고 Java/Spring 참여 인원이 1명으로 반영된다. A는 계속 리더이다. |
| 10 | B가 자신의 지원 결과와 승인 알림을 확인한다. | 해당 프로젝트의 승인 결과와 알림이 표시된다. |
| 11 | A·B가 새로고침하고 같은 결과를 다시 확인한다. | 승인 상태와 팀원 등록 결과가 유지된다. |

알림은 단계 6에서 A에게, 단계 8에서 B에게 전달되는지를 함께 확인한다. **실시간 도착과 목록 저장은 별도 항목**으로 기록하며, 확인 방법은 E2E-04를 따른다.

## 3. E2E-02: 거절된 지원자는 팀원으로 추가되지 않는다

**시작 조건:** E2E-01을 마쳤고 모집 인원이 남아 있다. C는 해당 프로젝트에 지원한 이력이 없는 상태이다.

| 순서 | 진행할 행동 | 기대 결과 |
| --- | --- | --- |
| 1 | C로 로그인해 같은 프로젝트를 열고 Java/Spring에 지원한다. | 지원이 접수되고 대기 상태가 된다. |
| 2 | A가 C의 지원 내용을 확인한다. | C의 정보와 지원 내용이 표시된다. |
| 3 | A가 C의 지원을 거절한다. | C의 지원 상태가 거절로 바뀐다. |
| 4 | 팀원 목록과 참여 인원을 확인한다. | C는 팀원에 없고 B는 그대로 남아 있다. Java/Spring 참여 인원은 1명이다. |
| 5 | C가 자신의 결과와 알림을 확인하고 새로고침한다. | 거절 결과와 해당 프로젝트 알림이 확인되고 상태가 유지된다. |

앞선 시나리오가 실패해 시작 조건을 만들지 못하면 진행 불가로 기록한다.

## 4. E2E-03: 로그아웃 후 회원 전용 기능을 사용할 수 없다

**시작 조건:** B가 로그인한 상태이다.

1. B가 로그아웃한다.
2. 내 프로필 등 회원 전용 화면에 다시 접근한다.
3. 로그인 안내가 나오거나 접근이 제한되는지 확인한다.
4. 뒤로가기로 이전 화면이 보이면 새로고침해 회원 전용 정보를 다시 사용할 수 있는지 확인한다.

공개 프로젝트 상세 화면이 보이는 것만으로 로그아웃 실패라고 판단하지 않는다. 로그아웃 이후에도 회원 전용 동작이 실제 완료되면 실패이다.

## 5. E2E-04: 실시간 알림과 알림 목록을 나눠 확인한다

E2E-01·02의 지원·승인·거절 **직전에** 알림을 받을 사람의 화면을 열어 둔다.

1. 현재 알림과 관찰 시작 시각을 기록한다.
2. 다른 사람의 브라우저에서 지원·승인·거절 중 해당 행동을 진행한다.
3. 받는 사람의 화면을 새로고침하지 않고, 미리 정한 시간 동안 새 알림이 나타나는지 본다.
4. 이후 알림 목록에서 프로젝트와 처리 결과가 맞는지 확인한다.

| 별도 기록 항목 | 확인할 내용 |
| --- | --- |
| 실시간 도착 | 새로고침 없이 새 알림이 나타나는가 |
| 목록 저장 | 알림 목록에서 해당 프로젝트와 결과를 확인할 수 있는가 |

목록에만 있으면 실시간 전달까지 통과한 것이 아니다. 화면에 실시간 알림을 확인할 방법이 없으면 그 항목은 진행 불가이다. 알림 목록 조회가 읽음 상태를 바꿀 수 있으므로, 실시간 관찰을 끝낸 다음 목록을 연다.

## 6. E2E-05: 잘못된 입력·행동을 막는다

정상 흐름과 구분해 새 프로젝트에서 확인한다. 각 행을 E2E-05-A~D로 따로 기록한다.

| 번호 | 준비와 행동 | 기대 결과 |
| --- | --- | --- |
| A | 로그인한 회원이 새 프로젝트 이름을 비우고 등록을 시도한다. | 필요한 입력을 안내하고 프로젝트는 생성되지 않는다. |
| B | 로그인하지 않은 별도 브라우저에서 프로젝트 등록·지원을 시도한다. | 로그인 안내 또는 접근 제한이 나오고 등록·지원이 완료되지 않는다. |
| C | 새 프로젝트에 B가 지원해 대기 중인 상태에서 다시 지원을 시도한다. | 중복 지원이 추가되지 않는다. |
| D | A가 만든 프로젝트에 A가 직접 지원을 시도한다. | 자기 프로젝트에 지원할 수 없다. |

버튼이 숨겨지거나 비활성화된 결과는 화면에서의 차단으로 기록한다. 서버가 직접 요청까지 차단하는지는 이 수동 시나리오만으로 판단하지 않는다. 화면에서 시도할 수 없는 항목을 서버 검증 통과로 쓰지 않는다.

## 7. 결과 기록과 마무리

실행 날짜와 회차를 구분한 별도 기록을 남긴다. 실행 명령 대신 수행 순서를 적고 다음을 함께 남긴다.

- 테스트 웹주소·브라우저·실행 시각·확인 가능한 배포 버전
- 사용자 구분 A/B/C와 프로젝트 이름·주소
- 시나리오 번호·멈춘 단계·기대 결과·실제 결과
- 통과 / 실패 / 진행 불가 / 미실행 판정과 민감정보를 가린 화면
- 알림 관찰 시간과 실시간 도착·목록 저장 각각의 결과

확인하지 못한 단계는 통과로 처리하지 않는다. 실패하면 처음 달라진 단계와 재현 순서를 적는다. 테스트 데이터 정리는 담당자와 범위를 확인해 진행하고 기존 회원·다른 사람의 프로젝트는 삭제하지 않는다.
