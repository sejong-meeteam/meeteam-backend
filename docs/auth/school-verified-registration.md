# 학교 확인 정보로 회원가입 및 기존 회원 학과 보충

## 범위

신규 학생 가입 시 사용자가 입력한 이름 대신 학교 포털에서 확인한 이름·학과를 저장합니다. 이름 비공개/별명/투표 기능은 이번 변경에 포함하지 않습니다. 기존 회원의 이름이나 학교 확인 상태를 자동으로 덮어쓰지 않습니다. 관리자·공용 테스트 계정은 기존 전용 로그인 경로를 유지합니다.

## 처리 흐름

1. 기존 학생의 학과가 비어 있으면 로그인과 같은 전용 세션에서 학교 프로필을 선택적으로 조회하여 학과만 보충합니다. 이름·학교 이름 확인 상태·이름 비공개 설정은 변경하지 않습니다. 이미 학과가 있거나 제한된 계정이면 기존 로그인 전용 검증을 유지합니다. 관리자·공용 테스트 계정은 별도 기존 경로를 유지합니다. 선택 조회가 실패해도 학교가 명시적으로 `OK`를 반환한 경우에만 기존 로그인 성공을 유지하며, 인증 실패·모호한 결과·입증되지 않은 UNKNOWN 결과는 로그인으로 인정하지 않습니다. 비밀번호 제출은 한 번이며 인증을 재시도하지 않습니다.
2. 요청 전용 쿠키 컨텍스트에서 공개 로그인 페이지를 먼저 열어 초기 세션을 만든 뒤 학교 로그인과 `GET https://portal.sejong.ac.kr/user/index.do`를 수행합니다. 프로필이 필요 없는 기존 로그인은 `mainLogin=N`, 신규 가입 및 학과 보충을 위한 프로필 조회는 실제 공개 로그인 폼과 같은 `mainLogin=Y`를 사용합니다. 오류 처리 분기에 등장하는 문자열이 아니라 실제 `result` 대입값을 읽습니다. 신규 조회에서 결과 형식이 불명확해도 로그인 성공으로 인정하지 않고, 다음 고정 프로필 요청의 학번 일치까지 확인해야 합니다. 신규 로그인에는 공개 페이지에서 확인한 고정 `rtUrl`을 전달하고, 같은 호스트의 `/comm/member/user/ssoLoginProc.do`를 호출한 뒤 프로필을 조회합니다. SSO 응답 본문이나 Location을 실행/추적하지 않습니다.
3. 서버 HTML의 단일 `div.text01` 카드에서 `span.txt1` 이름, `txt2` 학번, `txt3` 학적 구분, `txt4` 학과를 확인합니다. 학번이 로그인 요청과 다르거나 필드가 없고 중복/불완전하면 가입 코드를 발급하지 않습니다.
4. 확인된 이름·학과·학번을 일회용 가입 코드에 묶어 Redis에 10분간 저장합니다. 비밀번호, 학교 쿠키, 학교 원문 HTML은 저장하지 않습니다.
5. 신규 로그인 응답의 `verifiedProfile`을 프론트가 읽어 학교 정보를 수정 불가로 표시합니다.
6. 가입 시 서버가 코드를 원자적으로 소비하고, 저장된 학교 정보로 회원을 생성합니다. 요청에 포함된 기존 `name` 필드는 호환 목적으로만 받아 무시합니다. 학교 정보가 없는 구형 코드는 다시 로그인해야 합니다.

신규 로그인 응답 예시(합성 자료):

```json
{
  "isNewMember": true,
  "code": "<일회용 가입 코드>",
  "verifiedProfile": {
    "studentId": "20261234",
    "name": "테스트 학생",
    "department": "테스트학과"
  }
}
```

기존 사용자 로그인 응답에는 `verifiedProfile`을 추가로 노출하지 않습니다. 기존 `isNewMember`/`newMember` 직렬화 호환은 프론트 정규화에서 처리합니다.

## 프로필 수정과 저장

- `member.department`: 학교에서 확인한 학과. 기존 회원은 최초에 NULL이며 학과 보충이 성공한 다음 학교 로그인부터 채워집니다. 기존 값은 덮어쓰지 않습니다.
- `member.school_profile_verified`: 학교 이름·학과를 확인해 생성한 계정만 true. 기존 회원은 false.
- 학교 확인 계정의 이름은 일반 프로필 수정으로 바꿀 수 없습니다. 이름을 생략하거나 동일한 이름을 보내는 기존 클라이언트는 허용하고, 다른 이름이면 S3 조작 전에 거절합니다.
- 기존 미확인 계정은 기존 이름 입력·수정 흐름을 유지합니다. 관리자/테스트 계정을 학교 확인 계정으로 임의 전환하지 않습니다.
- 프로필 응답에 `department`와 `schoolProfileVerified`를 추가합니다.

## 전송·로그 보안

- 풀의 HTTP 연결은 재사용하지만 학교 쿠키 저장소는 매 요청 새로 생성하고 종료 시 비웁니다. 다른 사용자 및 익명 워밍업과 공유하지 않습니다.
- 기본 인증서·호스트 검증을 사용하며 TrustAll/Noop 검증을 사용하지 않습니다. 리다이렉트는 자동 추적하지 않습니다.
- 로그인 페이지와 프로필은 HTTP 200과 HTML 응답, 최대 약 1 MiB 본문, 필드 길이와 제어문자 여부를 확인합니다. 신규 로그인 POST의 302/303은 성공으로 간주하지 않고 Location도 추적하지 않습니다. 동일 세션의 고정 프로필 URL만 조회하여 학번 일치로 인증을 입증해야 합니다.
- 쿠키는 포털 호스트와 학교 부모 도메인만 허용합니다. 잘못된 쿠키를 라이브러리 경고 전에 거절하여 원문 Set-Cookie가 경고에 섞이지 않게 합니다.
- 새 학교 조회와 가입 코드 처리에서는 이름·학번·학과·가입 코드·학교 응답·비밀번호·쿠키를 로그에 출력하지 않습니다. 학교 프로필/가입 정보 객체의 toString은 가려진 설명만 반환합니다. 애플리케이션의 다른 기존 로그 전체를 감사한 것은 아닙니다.
- 프론트는 코드와 확인 정보를 sessionStorage 한 항목에 묶고 최대 10분 만료를 적용합니다. URL에 프로필이나 코드를 넣지 않습니다. 브라우저 저장값은 서버의 신뢰 근거로 사용하지 않습니다.

## 배포 순서와 제한

1. 실제 MySQL 백업/스키마 이력을 검토하고 별도 환경에서 V7을 먼저 검증합니다.
2. 승인 후 `V7__school_verified_member_profile.sql`을 적용합니다. 기존 데이터 삭제/재생성이나 Flyway 임의 활성화로 대체하지 않습니다.
3. 백엔드 배포 후 기존 로그인과 신규 학교 정보 조회를 확인합니다. 기존 프론트가 보낸 이름은 무시하므로 백엔드부터 적용할 수 있습니다.
4. 프론트 패치를 검토·적용하고 배포합니다. 프론트가 먼저 적용되면 이전 백엔드가 확인 정보를 주지 않으므로 신규 가입은 재로그인 안내로 중단됩니다.
5. 회원 생성, 학과 저장, 학교 이름 수정 차단을 실제 환경에서 별도로 확인합니다.

초기 변경 `2e3447f`는 실제 MySQL 임시 DB에서 V7/V8을 검증하고, 서버 내부 비공개 백업 후 기존 회원 컬럼 값 보존을 확인하여 적용·배포했습니다(GitHub Actions 실행 `43352601438`). 기존 회원 학과 보충 변경은 이와 별도의 후속 수정이며, 재배포 전에는 적용되지 않습니다. 이 후속 수정에는 새 스키마 변경이 없습니다.

브라우저의 로그인된 포털에서 이름·학번·학과가 서버 HTML에 포함되는 것을 확인한 뒤, 본인이 숨김 입력한 자격 증명으로 로컬 Java 17 도구의 실제 학교 로그인·SSO·프로필 수집을 검증했습니다. 최종 비식별 기록은 `LOGIN_RESULT_OK → SSO_HTTP_302 → PROFILE_HTTP_200 → PROFILE_VERIFIED → CHECK_PASSED`, 종료 상태는 `PASS`입니다. 요청 학번 일치와 이름·학과 필드 검증을 통과했으며 값 자체는 출력/저장하지 않았습니다. 초기 성공 판정과 누락된 SSO 연결을 보완한 뒤의 결과입니다. 이는 로컬 조회 검증이며, 이 로컬 기록 자체가 실제 서비스 서버의 학교 SSO 호출·실제 회원가입·기존 계정 학과 보충의 성공을 보장하는 것은 아닙니다. 실제 계정의 학과 보충은 수정본 반영 후 로그아웃하여 학교 로그인을 다시 수행하고 본인 프로필을 재조회해야 확인할 수 있습니다.

## DB를 바꾸지 않는 수동 학교 조회 확인

먼저 변경 코드로 Java 17 배포 JAR을 빌드한 뒤 일반 터미널에서 실행합니다.

```bash
java -Dloader.main=com.wardk.meeteam_backend.global.auth.client.SchoolProfileCheckTool \
  -cp build/libs/meeteam-backend-0.0.1-SNAPSHOT.jar \
  org.springframework.boot.loader.launch.PropertiesLauncher
```

학번과 학교 비밀번호는 터미널에서 숨김 입력합니다. 명령 인수, 채팅, 코드, 환경 파일에 넣지 않습니다. 한 번의 실제 학교 인증과 프로필 조회만 수행하고 성공 여부 및 고정된 단계/HTTP 상태/예외 종류 코드만 표시합니다. DB/Redis 접근, 회원가입, 개인정보 값 출력은 하지 않습니다. 선택적인 `meeteam.profile.check.diagnostics` 시스템 속성으로 지정한 파일에도 같은 비식별 코드만 저장하며 비밀번호나 응답 본문은 저장하지 않습니다. 기존 회원을 지우거나 탈퇴시켜 신규 가입을 시험하지 않습니다. 실제 학교 로그인/SSO 세션은 생성되거나 변경될 수 있습니다.

## 프론트 변경 전달

초기에는 프론트 main `c5c0e4b284d4205f1911b964011b101e3252d562` 사본을 기준으로 패치를 준비했습니다. 이후 원격 main `7395d08c8ebf793d61ed34da00c19b9227fc9942`에서 학교 확인 이름·학과 표시와 이름 비공개 연동 코드가 반영된 것을 확인했습니다. 이 후속 백엔드 수정은 기존 표시 계약을 유지하므로 별도 프론트 요청 필드나 API 추가가 필요하지 않습니다. 실제 사용자 화면에서의 학과 표시 완료는 재로그인 후 확인 대상입니다.

## 검증 기록

- 격리된 코드 사본에서 선별 백엔드 테스트 669개가 통과했습니다(실패/오류/건너뜀 0). 학교 세션·SSO·로그인 결과/쿠키 파서·가입 신뢰 경계·프로필 정책·V7 H2 호환 검사가 76개 포함됩니다.
- 기존 Cucumber/JUnit 호환을 위해 테스트 사본에만 JUnit 버전을 지정했습니다. 작업 저장소의 기존 build.gradle과 미완료 테스트 17개 파일은 보존했습니다. Java 작업자 연결 문제는 격리 실행의 IPv4 설정과 clean 재검증으로 해결했습니다.
- 게시된 원본 build.gradle을 사용한 Java 17 bootJar -x test도 성공했습니다. JAR의 시작 클래스는 기존 MeeteamBackendApplication이며, 수동 조회 도구는 터미널 없이 실행할 때 자격 증명 수집을 거부하는 것을 확인했습니다.
- 프론트 단위 테스트 150개, 회귀 테스트 13개와 타입 검사가 통과했습니다. 일부 변경 파일의 전체 lint에는 HEAD에도 존재한 기존 set-state-in-effect 오류 4개가 남습니다. 프론트 AGENTS.md 지침에 따라 전체 빌드는 실행하지 않았습니다.
- 본인의 숨김 입력을 통한 실제 학교 수동 확인은 최종 `PROFILE_VERIFIED`, `CHECK_PASSED`, 종료 상태 `PASS`로 성공했습니다. DB/Redis·회원가입 없이 학교 로그인/SSO/정확한 학번·이름·학과 조회만 검증했습니다. 선별 자동 테스트에는 운영 DB/Redis/실제 학교 계정 데이터를 사용하지 않았습니다.
- 운영 전 학교 포털 이용정책과 이름·학과 수집 안내/동의도 별도로 검토해야 합니다.

## 기존 회원 학과 보충 후속 검증

- 빈 학과 보충, 기존 이름/비공개 설정 유지, 이미 저장된 학과 보존, 계정 제한 유지, 조회 결과 학번 검증을 검사했습니다.
- 클라이언트는 한 번만 비밀번호를 제출합니다. 명시적 로그인 OK 뒤 SSO/프로필 조회가 실패하면 기존 로그인은 유지하고 학과는 다음 로그인 때 다시 시도합니다. UNKNOWN 결과는 정확한 인증 프로필 증명 없이 로그인으로 인정하지 않습니다.
- 선택적 SSO/프로필 조회의 연결·풀 대기·응답 타임아웃은 각각 5초입니다. 이는 전체 요청의 단일 5초 제한을 의미하지 않습니다.
- 신규 가입의 프로필 필수 정책과 관리자·테스트 계정 경로는 유지합니다.
- 격리 사본의 선별 테스트 711개 통과(실패/오류/건너뜀 0), Java 17 배포 JAR 빌드 성공. 운영 DB/실제 학교 자격 증명은 이 자동 테스트에 사용하지 않았습니다.
- 실제 사용자 계정의 보충 결과는 후속 배포 후 새 학교 로그인과 본인 프로필 조회로 확인해야 합니다. 기존 JWT 갱신이나 화면 새로고침만으로 학교 비밀번호 인증을 다시 수행하지 않습니다.
