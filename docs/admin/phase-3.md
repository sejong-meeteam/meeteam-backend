# 관리자 기능 3단계: 권한 변경과 강제 조치

> 대시보드와 프론트 계약 점검의 후속 구현은 [4단계](phase-4.md)를 참고하세요.

## 추가 API

| API | 응답 |
|---|---|
| PATCH /api/v1/admin/members/{id}/role | 갱신된 AdminMemberSummary |
| POST /api/v1/admin/members/{id}/withdraw | 갱신된 AdminMemberSummary |
| POST /api/v1/admin/projects/{id}/close | 갱신된 AdminProjectSummary |
| POST /api/v1/admin/projects/{id}/members/{memberId}/expel | 갱신된 AdminProjectSummary |

모든 요청에 trim 후 5~200자 사유가 필요합니다. 권한은 USER/ADMIN 문자열만 허용하며, JSON 타입을 임의로 바꾸지 않습니다.

## 보호 규칙

- 관리자 권한은 URL 검사에 더해 변경 트랜잭션 안에서도 다시 확인합니다.
- 모든 관리자 조치는 관리자 행을 ID 순서로 잠근 뒤 대상 회원, 관련 프로젝트 순서로 잠급니다.
- 대기 중 권한이 바뀌면 이미 로드된 객체를 다시 읽고 ADMIN 여부를 검사합니다.
- 본인 권한 변경·강제 탈퇴는 ADMIN_SELF_ACTION입니다. 같은 상태와 탈퇴한 대상은 ADMIN_INVALID_STATE입니다.
- 마지막 활성 관리자 보호와 동시 상호 권한 해제 방지를 포함합니다.
- 테스트 로그인용 내부 예약 계정은 기존 재기동 안전 조건을 유지하기 위해 권한 변경·강제 탈퇴를 거절합니다. 데모용 일반 회원 전체를 보호하는 규칙은 아닙니다.
- 모든 변경과 감사 로그는 같은 트랜잭션이며, 로그 저장 실패 시 변경도 취소됩니다.

## 동작

### 권한 변경

실제 역할을 변경하고 authVersion을 증가시킵니다. 대상의 기존 access/refresh 토큰은 무효가 되어 다시 로그인해야 합니다. 정지 기간과 사유는 유지합니다.

### 강제 탈퇴

- VISIBLE 프로젝트의 생성자라면 MEMBER_HAS_LED_PROJECTS로 거절합니다. 먼저 프로젝트를 숨기거나 삭제해야 합니다.
- HIDDEN/DELETED 프로젝트의 생성자 정보는 기록을 위해 남깁니다.
- 지원서 중 PENDING만 CANCELLED로 변경합니다. 승인/거절된 기록은 지우지 않습니다.
- 공개 여부와 관계없이 참여 프로젝트의 팀원 관계를 제거하고 실제 모집 인원을 조정합니다. 리더를 별도 모집 인원으로 잘못 차감하지 않습니다.
- 모집 강제 마감과 리더 모집 중단을 팀원 제외 때문에 자동으로 풀지 않습니다.
- 회원 레코드·질문·이미지 등을 하드 삭제하지 않습니다.
- 일반 자진 탈퇴와 구분하는 adminWithdrawn 표시를 저장합니다. 강제 탈퇴 계정은 포털 인증에 성공해도 로그인 401이며, 탈퇴 전에 발급된 가입 코드로 재가입하는 것도 차단합니다.
- 기존 자진 탈퇴 후 재가입 흐름은 유지합니다. 모든 탈퇴 종류에 일괄 적용하는 401 정책은 별도 합의가 필요합니다.

### 모집 강제 마감·팀원 강제 제외

- 강제 마감은 모든 포지션을 닫고 모집 상태를 CLOSED로 설정합니다. 노출 상태는 바꾸지 않습니다.
- 대기 지원서는 그대로 두며 리더가 처리합니다.
- 팀원 제외는 리더를 대상으로 할 수 없습니다. 숨김·삭제 프로젝트도 관리자 조치는 가능합니다.
- 실제 팀원 관계와 모집 인원을 함께 변경합니다. 수동으로 닫힌 포지션을 자동으로 다시 열지 않습니다.

## 동시 요청과 공개 목록

- 지원/승인/팀원 추가/프로젝트 생성은 대상 회원부터 잠그고 활성 상태를 다시 확인하여 강제 탈퇴와 경합할 때 뒤늦게 가입 관계가 생기지 않도록 합니다.
- 프로젝트 팀원 제거도 프로젝트 잠금을 공유하여 모집 인원의 이중 차감을 방지합니다.
- 기존 익명 메인 페이지의 전체 카드 캐시는 사용하지 않습니다. 캐시 무효화 직전 시작한 읽기가 숨김 전 결과를 다시 캐시하는 경우까지 막기 위해 최신 DB 노출 조건을 매번 조회합니다. 성능 최적화는 정책에 안전한 방식으로 별도 검토합니다.

## DB 변경과 검증 범위

- V3 정지·노출 상태·감사 로그 변경에 더해 `V4__admin_withdrawal_marker.sql`의 member.admin_withdrawn 컬럼이 필요합니다.
- 아직 실제 서버에 SQL을 적용하지 않았습니다. V3/V4와 기존 Flyway 이력 및 백업을 검토하지 않고 바로 배포하면 안 됩니다.
- 검증은 H2 임시 DB와 가짜 외부 의존성을 사용합니다. 실제 MySQL 마이그레이션과 프론트 연결 검증은 별도입니다.
- 기존 미완료 테스트와 build.gradle 변경은 보존합니다. 전체 인수·통합 테스트를 통과했다는 뜻은 아닙니다.

## 남은 작업

- 관리자 대시보드 조회와 실제 프론트 연결.
- V3/V4의 격리된 MySQL 적용 및 스키마 검증.
- GitHub 연동과 관리자 강제 제외/탈퇴 이후 저장소 권한 회수. 이번에는 GitHub API를 호출하거나 권한 회수가 완료됐다고 처리하지 않습니다.
- 탈퇴한 생성자가 남은 숨김 프로젝트를 복구할 때의 운영 정책과 신규 관리자 최초 생성 절차 검토.
