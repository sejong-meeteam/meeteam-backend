# 관리자 기능 4단계: 대시보드와 프론트 계약 점검

> 이후 실제 MySQL과 로컬 프론트의 검증 결과는 [5단계](phase-5-validation.md)를 참고하세요. 아래 연결 전 확인사항은 4단계 당시 기준입니다.

## 추가 API

`GET /api/v1/admin/dashboard` — ADMIN 전용, 기존 성공 응답의 result에 아래를 반환합니다.

- stats: totalMembers, newMembersToday, suspendedMembers, totalProjects, recruitingProjects, hiddenProjects, pendingApplications
- recentMembers: 최근 가입 회원 최대 5개, 목록과 같은 학번 마스킹 및 이미지/직무 매핑
- recentProjects: 최근 생성 프로젝트 최대 5개, 숨김 포함·삭제 제외
- recentAuditLogs: 최근 조치 최대 5개

## 집계 기준

- 전체 회원: 탈퇴하지 않은 회원. 관리자와 정지 회원도 포함합니다.
- 오늘 신규 가입: 서울 기준 오늘 00:00 이상, 다음 날 00:00 미만의 createdAt이며 탈퇴하지 않은 회원.
- 정지 회원: 현재 유효한 정지 상태이며 탈퇴하지 않은 회원. 만료 시각과 같으면 이미 해제된 것으로 셉니다.
- 전체 프로젝트: DELETED 제외. HIDDEN은 포함합니다.
- 모집 중: VISIBLE이며 저장된 모집 상태가 RECRUITING인 프로젝트.
- 숨김 프로젝트: HIDDEN.
- 대기 지원서: 전체 PENDING. 숨김·삭제 프로젝트에 남아 있는 대기도 포함합니다.

기존 백엔드의 모집 상태 저장값을 사용합니다. 프론트 MSW가 마감일·포지션 정보를 추가로 해석하는 부분과 실제 백엔드의 자동 마감 정책은 실연결 시 별도로 대조해야 합니다.

## 구현 및 검증

- SQL 집계를 사용하며 전체 회원/프로젝트를 메모리에 올려서 세지 않습니다.
- 최근 항목은 DB에서 5개로 제한합니다. 생성 시각 내림차순, 동률이면 ID 내림차순입니다.
- 회원 직무는 한 번에 조회하고 기존 요약 매퍼를 재사용합니다. 감사 로그 조회도 기존 서비스를 재사용합니다.
- 읽기 전용 REPEATABLE_READ 트랜잭션으로 지표와 최근 목록의 DB 시점을 맞춥니다.
- 시간은 한 번 캡처합니다. 통계와 최근 회원의 정지 상태를 같은 시각으로 판단합니다.
- Clock을 분리하여 UTC 날짜와 서울 날짜가 다른 경우와 자정 경계를 테스트합니다.
- 조회 과정에서 만료된 정지 기록이나 다른 레코드를 수정하지 않습니다.

## 프론트 계약 대조

확인한 기준은 프론트 c5c0e4b의 types/admin.ts, components/features/admin/adminApi.ts, dashboard/AdminDashboardPage.tsx, 기존 Next 프록시입니다.

- 관리자 API의 13개 경로와 요청 메서드/본문, result 응답, 목록 메타데이터를 소스 수준에서 대조했습니다.
- 대시보드 4개 최상위 필드와 7개 통계 필드를 MockMvc에서 검증합니다.
- 권한 없는 요청은 조회 서비스 호출 전에 401/403으로 차단합니다.
- 프론트의 pendingApplicationCount%2Cdesc 링크가 MVC에서 쉼표를 포함한 정렬값으로 해석되는지 검증합니다.
- 알 수 없는 필터를 기본 조건으로 처리하는 정책은 backend-handoff.md에 따른 의도된 동작입니다.

**프론트를 실제 백엔드에 연결해 화면을 검증한 것은 아닙니다.** 프론트 파일·배포 환경변수·MSW 설정은 변경하지 않았습니다.

## 실제 연결 전에 필요한 확인

1. 격리한 MySQL 8에서 V3/V4와 기존 Flyway 이력, Hibernate validate, 데이터 보존 검증.
2. 기존 createdAt이 어느 시간대로 저장됐는지와 서버 JVM 시간대 확인. 서울 날짜 집계와 DB 저장 시간대를 맞추되 기존 날짜를 임의로 변환하지 않습니다.
3. 명시적으로 승인된 첫 관리자 계정 준비. 데모/MSW 관리자 계정이 서버에 자동으로 생기는 것은 아닙니다.
4. 프론트 API 원점과 프록시 쿠키 전달을 확인하고, 검증 환경에서 MSW를 끈 뒤 실제 로그인/조회/변경을 점검.
5. 위 검증과 승인 후에만 커밋·푸시·DB 적용·배포를 진행.

관리자 API 작성 단계와 실제 운영 연결 완료는 구분합니다. GitHub 연동과 저장소 권한 회수는 아직 구현하지 않았습니다.
